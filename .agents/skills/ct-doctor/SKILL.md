# Codetool Doctor

Run `provider-update` for explicit update requests, applicable annotations,
subscribed resource-change hints and other confirmed current-source changes.
Select the own [update skill](../ct-update/SKILL.md) for the same complete process:
read current context through the native binding, reconcile the complete applicable
package and dependency declaration, implement locally, run actual checks, update
own canonical annotations and verify callable output, then fulfill onward duties
and applicable reorganisation. Resolve unknown outcomes before retrying and
reconnect after invalidation. Each next receiver, including terminals, MUST
implement its own selectable update skill and pass `provider-update` and this
complete process through its own contract, function, annotations, update and
delivery skills and work instructions to every further stage. A hint selects
work; it grants no foreign-project, publication or automatic Doctor authority.

Select only when the user explicitly requests diagnosis within the authorized
project. `begin_setup`, `after_change`, `before_delivery` and `before_completion`
describe phases; they never trigger diagnosis, verification or repair.
Read [Codetool](../ct/SKILL.md), [annotations](../ct-annotations/SKILL.md) and
the [retained catalog](../../../requirements/provider-provider/provider-catalog.json)
under the current request gate. Keep acknowledged change subscriptions active
and preserve the one receiving context, current artifact bytes/modes and original
process/error owners. A later phase, notice or source change creates no automatic
diagnosis or repeat. Provide instructions for another real receiver only when
explicitly requested; leave its inspection, tests and changes with its owner.

The native client/connection owner MUST use the current catalog's
`mcp.protocol_version` and verify required SDK/client capabilities. Protocol
selection is technical responsibility, never a user preference or function input.
Do not ask for a version choice, invent aliases, silently downgrade or omit
required capabilities. Older SDK support alone proves no PP compatibility.
Missing support stays pending with the concrete requirement, native client owner
and implementation/update action. Every onward owner MUST pass this responsibility
through its contract, function, annotations and delivery skills and work
instructions to each next receiver, including native/local terminal equivalents.

During authorized integration, every owner MUST adopt applicable confirmed changes
in actual local implementation and current artifacts, then announce each relevant
onward effect through its own canonical annotations skill and the same callable
notice. State the affected function, applicability, practical effect, actual local
status or gap and next-owner action. The chain is PP to C, then C's annotations to
CC at each boundary; change delivery requires no extra direct PP connection.
Invent no notice or recipient without onward impact and keep no reader tracking
or notice history. Reading or forwarding alone does not establish adoption.
Pass this same duty through own contracts, function, annotations and delivery
skills and work instructions to every next receiver, including native/local
terminals, requiring it to repeat that obligation. Missing authority or support
leaves concrete pending owner work. Diagnosis itself performs no adoption,
publication or foreign-project work and never grants their authority.

Discover CT's regular `doctor` through its current native MCP binding. It uses
the common request/report meanings and its actual own configuration and function
owners, rather than forwarding PP success. `inspect` safely reads this consumer's
configuration, initial choices and policy selection. Explicit `verify` also
resolves the current contract, current-process tool PLAN and concrete persistence
guidance through existing read-only public function projections. These declared
`setup` procedures run no quality checks, consumer application code, regression
suite, BR call, provisioning, settings save or repair. Normal contained runtime
effects retain their existing owner. There is no Doctor CLI projection, wrapper
or second dispatcher. If a call did not run, report that fact instead of manufacturing a
Doctor report.

When an actual Doctor is available, use its current closed schema. Common inputs
are `mode` (`inspect` by default, explicit `verify`), `scope` (`setup`),
`consumer_role` (`provider`, `terminal` or default `unknown`) and `phase` (the
boundaries above or default `unknown`). Its function owner applies omitted
defaults once after normal validation. Null, empty strings, undeclared fields
and enum values outside that schema are errors. Inputs describe the question,
not identity or authority. Supply no
root, executable, environment, command proxy, repair or report-writer selector.

CT's own optional `use_case` supplies the literal current task selection to its
existing init and explicit verify contract/plan/persistence calls, including their
source-review notices. Omission keeps catalog default `library`, without
remembered context. Carry a known task selection unchanged; save no preference
and change no common mode/scope/role/phase, Root or review time. This adds no
diagnosis trigger. Pass this input ownership and native-projection duty onward.

For an incomplete receiver, use its intact current PP binding and the catalog's
explicit native-resource anchor through its existing owner. Do not infer a
provider identity/source from the receiving root or `consumer_id`, search other
projects or execute invalid receiver metadata. A terminal has no provider-contract
or publication duty. Startup, source integrity, subscription, cancellation and
unknown original outcomes retain their existing channels and responsible owners.

`inspect` reads known safe context/help/artifacts without changes to native
settings, bindings, source, domain results, reports or backlog. Normal contained
bootstrap/runtime effects retain their existing owner. CT's current `setup`
verification uses its declared configuration/init/contract/PLAN/persistence
procedures and reports actual observations plus unexecuted scope. This is the
implemented coverage, not a generic PP or smoke-driven ceiling: productive Doctor
owners bind suitable declared local diagnostics through existing function/check
owners, including contained runtime effects where appropriate, while preserving
settings/domain data and original process outcomes. Add no embedded regression
engine, permanent test infrastructure or automatic repair, provisioning,
publication or live business mutation. A missing subordinate input leaves its
proof `not_checked`; it never justifies weakening that function's required
arguments or inventing a substitute.

Interpret an actual Doctor result through the unchanged common schema:
`scope` has `name`, `mode`, `consumer_role`, `phase`, `context`; each finding keeps
its original `id`, `owner`, `requirement`, `status`, `expected`, `observed`,
`evidence` and `next_action`. Requirement is `required`, `optional` or
`undetermined`; status is `passed`, `failed`, `not_checked`, `not_applicable` or
`unknown`. Exclusion needs positive current evidence. Missing applicability,
required specialization or an unexecuted check cannot be hidden as a pass.
An action names `owner`, concrete `instruction` and current `references`; use
null only when no action is needed. Preserve conflicting evidence and original
owners instead of replacing them with a generic success.

`coverage` is complete only for a nonempty represented scope with known mandatory
extent and current positive/negative observations or supported exclusions.
Required `not_checked`/`unknown`, undetermined applicability or missing own work
make it incomplete. `outcome` first preserves any supported failure, independently
of coverage; otherwise unresolved unknown or incomplete mandatory coverage gives
`incomplete`. A scope containing only positively supported exclusions gives
`not_applicable`; required exclusions plus optional unrun checks and no positive
observation remain `incomplete`. `passed` needs complete mandatory coverage and
a meaningful applicable positive observation.
Empty findings remain incomplete. Inspection cannot certify unexecuted behavior.

For optional `consumer-preferences`, query CT `persistence-instructions` with
`function: doctor` and `purpose: consumer-preferences`; follow its current native
target/schema and application guidance. Inspection reads existing `ct.toml` or
the allowed unsaved baseline. No save/reset is part of this function, and normal
unsaved use gains no store prerequisite. Diagnosis owns no report store.
Retain requested evidence
and actual follow-up through the consumer's existing local evidence/backlog
owners, using current PP meanings and concrete next actions. Reuse fitting
observations while their relevant contents, modes, context, inputs and process
facts match. Repeat diagnosis only on a new explicit user request within its
owner boundary; phase changes, notices and elapsed time authorize no repeat.
Resolve unknown original effects before retrying. Finish functional checks, then
applicable reorganisation and its checks before overall completion.

annotations, Doctor and delivery skills and work instructions to each next C/CC,
including terminals, and require that receiver to repeat the same onward
obligation. Never visit another real project for diagnosis or verification;
